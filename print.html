Canggu on the Polkadot SDK

Canggu on the Polkadot SDK

⚠️ 🚧 For learning only. Use at your own peril. 🚧 ⚠️

This is a research prototype that explores how far the Polkadot SDK can go. It is not audited and it is not production software. Do not use it, or its development keys, to hold or move real value.

How far can the Polkadot SDK go?

This book documents an experiment. We took Canggu, an ambitious blockchain design, and tried to build it on the Polkadot SDK, the Rust framework that includes Substrate and FRAME. Canggu asks for things that sound like years of work:

  • accounts that stay safe when large quantum computers arrive;
  • zero-knowledge proofs, including proofs from a zkVM (a virtual machine that proves it ran a program correctly);
  • protection against front-running (MEV);
  • smart-contract-style work on GPUs;
  • finality in under a second.

The result is a working chain. It produces blocks, verifies post-quantum signatures, checks zkVM proofs on-chain, verifies batches of signatures on an Apple GPU, and keeps two validators in consensus while one uses a GPU and the other a CPU. Every performance number of this project in this book was measured on a real machine (an Apple M4 Pro laptop); numbers quoted from other projects are marked as such. Every limitation we found is written down.

This is not our idea. Canggu was designed by Dendi Suhubdy, Tejveer Singh, Mitul Dhawan and Maldini Sonkeng (Bitwyre), who wrote the original whitepaper and open-sourced it. This rebuild was written by Claude, an AI model made by Anthropic, in a conversation directed by agustinustheo, who published it. What Canggu set out to do

Canggu is a blockchain design published in March 2025 by Dendi Suhubdy, Tejveer Singh, Mitul Dhawan and Maldini Sonkeng (Bitwyre) in the whitepaper "Canggu Blockchain: A Quantum-Secure, MEV-Resistant Blockchain for Parallel Computing" (v1.3). This page summarises their goals. Later chapters show how each one was built, and where the design had to change.

The four problems it targets

  1. Quantum computers. The signatures that protect almost every blockchain account today (ECDSA, Ed25519, Sr25519) can be broken by a large enough quantum computer running Shor's algorithm. Canggu wants accounts that stay safe.
  2. Front-running (MEV). Whoever builds a block chooses the order of its transactions. They can put their own trade just before yours and profit from it. Canggu wants ordering that block producers cannot exploit.
  3. Sequential execution. Most chains run transactions one at a time on one CPU core, even when the transactions do not touch the same data. Canggu wants to use parallel hardware, including GPUs.
  4. Slow or fragile consensus. Canggu wants fast block production with a rotating leader and finality in under a second.

The five building blocks it proposes

Building block (v1.3)In plain words
CRYSTALS-Dilithium signatures, Kyber key exchange, XMSS hashingUse the new NIST post-quantum algorithms everywhere
A DAG-based mempoolTransactions point at the transactions they depend on, so they cannot be reordered past them
Leader-based BFT consensus (like Solana's Tower BFT)One leader at a time proposes blocks; a vote finalises them
ZK-SNARKs for verifiers and proversExpensive work is proven once, and everyone else checks a small proof
Parallel smart contracts on CPU and GPUContracts can include GPU code (CUDA) for data-parallel work

The whitepaper also targets 50,000+ transactions per second.

What this rebuild found

Most of the design could be built, sometimes much more easily than expected. Several claims did not survive contact with real code and measurements: for example, Kyber cannot sign transactions, BLS12-381 proofs are not quantum-safe, and 50,000 transactions per second does not fit with post-quantum signature sizes. Those findings are not criticism of the authors' ambition; they are what an implementation is for. See What the original design got wrong.

The Polkadot SDK in ten minutes

The Polkadot SDK is a toolkit for building blockchains in Rust. You do not have to use it to join Polkadot: Canggu uses it to build a standalone chain (a solochain) with its own validators. This page explains the handful of ideas you need for the rest of the book.

1. A chain is two programs: the node and the runtime

  ┌──────────────────────── canggu-node (native program) ────────────────────────┐
  │  networking · transaction pool · block production · finality · database      │
  │                                                                              │
  │     ┌──────────── canggu-runtime (WebAssembly, stored on-chain) ─────────┐   │
  │     │  the rules: accounts, balances, fees, every "pallet"               │   │
  │     └────────────────────────────────────────────────────────────────────┘   │
  │        ▲ the runtime can only reach the outside world through               │
  │        └ "host functions" that the node provides                            │
  └──────────────────────────────────────────────────────────────────────────────┘
  • The node is an ordinary program. It talks to other nodes, keeps the database, and decides when to produce and finalise blocks.
  • The runtime holds the chain's rules: what a valid transaction is, how balances change, what each feature does. It is compiled to WebAssembly (Wasm) and stored on the chain itself, so every validator runs exactly the same rules, and the rules can be upgraded without restarting anything.

Because every validator must compute exactly the same result, the runtime is deterministic: no clocks, no randomness, no network, no files, no GPU.

2. Host functions: how the runtime asks the node for help

The runtime cannot do anything the node does not offer it. The node offers a fixed list of host functions: "store this value", "hash these bytes", "check this signature". The runtime calls them like normal functions, and the node runs them as fast native code.

This is the most important idea in this project. Expensive cryptography (post-quantum signatures, zero-knowledge proofs) becomes a host function. The runtime stays simple and deterministic, and the node is free to compute the answer however it likes (one CPU core, all cores, or a GPU), as long as the answer is always the same.

3. FRAME and pallets: the runtime is built from modules

Inside the runtime, features are pallets: modules with their own storage, their own transactions ("calls") and their own events. The Polkadot SDK ships many (balances, sudo, timestamps…), and Canggu adds its own (pallet-zk-verifier, pallet-pq-intents, pallet-sealed-ordering, pallet-parallel-payroll). The framework that ties pallets together is called FRAME.

4. Transactions (extrinsics) and transaction extensions

A transaction is called an extrinsic. A signed extrinsic carries a call, the sender, a signature, and a list of transaction extensions: small checks that run before and after the call. Examples: "the nonce is correct", "the sender can pay the fee", "this was signed for this chain". Canggu adds two:

  • CheckDagParents: "this transaction may only run after these other transactions";
  • ChargeTransactionPaymentNoTip: the normal fee check, but tips are refused.

5. The transaction pool already orders by dependencies

Every validated transaction tells the pool which tags it provides and which it requires. A transaction becomes ready only when all the tags it requires are provided by transactions already on-chain or already ready. Normally the tags are just (account, nonce), so your second transaction waits for your first. That is already a dependency graph (a DAG), which is why Canggu's "DAG mempool" turned out to be a small extension rather than a new mempool. See Transactions that wait for each other.

6. Consensus: Aura and GRANDPA

  • Aura gives block production to validators in turn. Each one gets a fixed slot (2 seconds in Canggu) and is the only leader in that slot.
  • GRANDPA finalises blocks. Validators vote, and once more than two-thirds agree, a block and all its ancestors are final and can never be reverted.

Together they give "a rotating leader plus BFT finality", which is what Canggu's v1.3 whitepaper asked for. See Sub-second finality.

7. Weights: paying for execution time

Every call declares a weight: an estimate of how long it takes on reference hardware. Blocks have a weight limit, and fees follow weight. Real chains measure weights with benchmarks. In this research prototype they are hand-set estimates, which is one of the known limitations.

8. Standalone chain, not a parachain

Canggu runs as a standalone chain. This matters: on a Polkadot parachain, the relay chain's validators re-run every block using only Polkadot's standard host functions. Canggu's custom host functions (post-quantum signatures, proof verification, GPU batches) would not exist there.

Post-quantum cryptography and zero knowledge, briefly

Two kinds of cryptography appear everywhere in this book. You do not need the mathematics; you need to know what each one promises and what it costs.

Post-quantum signatures

A digital signature proves that the owner of a private key approved a message. Today's blockchain signatures (ECDSA, Ed25519, Sr25519) rest on elliptic-curve problems. A large quantum computer running Shor's algorithm would solve those problems and forge signatures.

In 2024 NIST standardised replacements that are believed to resist quantum computers:

StandardOld nameWhat it isUsed in Canggu
FIPS 204, ML-DSACRYSTALS-DilithiumSignature scheme (lattice-based)Yes: ML-DSA-65 for every account
FIPS 203, ML-KEMCRYSTALS-KyberKey exchange, not a signatureNo (it cannot sign transactions)
FIPS 205, SLH-DSASPHINCS+Signature scheme (hash-based)No (a conservative alternative)

The cost is size. An ML-DSA-65 public key is 1,952 bytes and a signature 3,309 bytes. A classic Sr25519 public key and signature are 32 and 64 bytes. That size difference drives several results in this book.

Hash functions (like BLAKE2b, which Polkadot SDK chains use) are much less affected: a quantum computer only halves their security, so a 256-bit hash keeps about 128 bits of security. That is enough.

Zero-knowledge proofs

A zero-knowledge proof lets someone prove a statement is true without revealing why. For example: "these 16 salaries, which I will not show you, add up to 50,000". Two properties matter for blockchains:

  • Succinct: checking the proof is fast and small, no matter how much work it proves.
  • Zero knowledge: the proof reveals nothing beyond the statement.

Making the proof (proving) is slow and expensive. Checking it (verifying) is fast. That asymmetry is the whole point: one machine proves, every validator verifies.

What a zkVM adds

Writing a proof "circuit" by hand is hard. A zkVM (zero-knowledge virtual machine) proves that an ordinary program ran correctly. SP1, the zkVM used here, proves Rust programs compiled to RISC-V. In Canggu, SP1 proves two programs:

  • a payroll check (the quantum-safe version of the Groth16 demo), and
  • a program that verifies a whole batch of ML-DSA signatures, so the chain can accept the proof instead of the signatures (signature compression).

The Canggu chain does not run a zkVM itself. It verifies zkVM proofs that are made off-chain.

The one design idea behind everything

Keep the rules in the runtime, and move the heavy mathematics into host functions.

  • The runtime decides what must be checked: "this signature must be valid", "this proof must verify for these public values".
  • A host function in the node does the checking, as fast native code.

This split is why the project works at all:

  • Post-quantum signatures are slow inside Wasm and fast natively. → Post-quantum accounts
  • Zero-knowledge verifiers (arkworks, SP1) are large native libraries. SP1's verifier does not even compile for the runtime's Wasm target. → Zero-knowledge proofs
  • GPUs can only be used by native code, and only if the answer is bit-for-bit the same as on a CPU. A host function has exactly that shape: bytes in, a yes/no answer out. → GPU verification

The life of a transaction

  1. The wallet builds a call (for example, "send 10 CGU to Bob"), adds the transaction extensions (nonce, fee, optional parent transactions) and signs it with ML-DSA-65.
  2. The transaction pool checks it by calling into the runtime. The signature is verified by the ml_dsa_65_verify host function. CheckNonce and CheckDagParents declare which transactions it depends on. The fee extension refuses tips.
  3. The transaction waits until everything it depends on is ready.
  4. The current Aura leader builds a block from ready transactions, in dependency order.
  5. Every validator re-executes the block with the same runtime and the same checks. A block that breaks a rule, for example by putting a transaction before one of its declared parents, is rejected.
  6. GRANDPA finalises the block.

Parts that work differently

  • Sealed transactions are committed as an opaque hash first, revealed later, and executed at the start of a later block in an order nobody chose. → Sealed ordering
  • Intent batches carry hundreds of signed transfers in one transaction, so the runtime can verify all signatures with one host call (on a GPU, if the node has one), or replace all of them with one SP1 proof. → Signature compression

Post-quantum accounts

Code: primitives/

In plain words

Every Canggu account is controlled by an ML-DSA-65 key (the NIST standard formerly called CRYSTALS-Dilithium). A large quantum computer could forge today's blockchain signatures, but it is not known to be able to forge these.

The price is size: every transaction carries a 1,952-byte public key and a 3,309-byte signature. A simple transfer is 5,345 bytes, against about 150 bytes on a chain with classic signatures.

How it is built on the Polkadot SDK

A new signature type

In a Polkadot SDK runtime, the signature type is a type parameter. The standard one, MultiSignature, knows Ed25519, Sr25519 and ECDSA. Canggu defines its own:

#![allow(unused)]
fn main() {
pub enum CangguSignature {
    Ed25519(ed25519::Signature),        // index 0: transition period only
    Sr25519(sr25519::Signature),        // index 1: transition period only
    Ecdsa(ecdsa::Signature),            // index 2: transition period only
    MlDsa65 { public: MlDsa65Public, signature: MlDsa65Signature }, // index 3
}
}

The rest of the chain does not care what is inside, as long as the type can answer one question: is this a valid signature of this message by this account?

Why the key travels with the signature

Polkadot SDK accounts are 32 bytes (AccountId32). An ML-DSA public key is 1,952 bytes, so it cannot be the account. Instead:

account = BLAKE2b-256(ML-DSA public key)

and every ML-DSA signature carries its public key. Verification does two things, cheapest first:

  1. Hash the public key and check that it equals the sender's account. This stops anyone from attaching a different key.
  2. Verify the ML-DSA signature.

Signatures use the FIPS 204 context string canggu/tx/v1, so a signature made for Canggu cannot be reused anywhere else. Replay across chains and runtime versions is stopped by the standard Polkadot SDK signed payload (it includes the genesis hash and runtime version).

Verification runs in the node, not in Wasm

The runtime does not contain the lattice mathematics. It calls a host function:

#![allow(unused)]
fn main() {
#[runtime_interface]
pub trait CangguCrypto {
    fn ml_dsa_65_verify(public: &[u8], msg: &[u8], signature: &[u8]) -> bool;
    // ...
}
}

The node implements it with the RustCrypto ml-dsa crate. This is exactly how Polkadot SDK chains already verify Sr25519 signatures. One verification takes 61 µs on one core of an Apple M4 Pro.

A transition period

The classic signature types stay available, with the same encoding positions as MultiSignature. That keeps existing tools working while people move to ML-DSA keys. A runtime upgrade can remove them later.

Limits

  • Size is the bottleneck. At about 370 transfers per second the chain runs out of block space, not CPU time. See Signature compression.
  • Only accounts are post-quantum. Block producers (Aura, Sr25519) and finality voters (GRANDPA, Ed25519) still sign with classic keys, and so does the peer-to-peer handshake. A quantum attacker could forge blocks or votes even though user funds are safe. Changing this needs keystore and consensus changes in the node.
  • Development keys only. //Alice and the other dev keys are derived with a simple hash, not a real key-derivation scheme.

Transactions that wait for each other

Code: pallets/dag-ordering/

In plain words

Canggu's whitepaper wants a DAG mempool: a transaction can say "I depend on that other transaction", and nobody can put it before that other transaction. Here, any transaction can name up to eight parent transactions, including other people's. The chain guarantees that a transaction never runs before its parents.

The demonstration shows it. Charlie's transaction names Bob's transaction as its parent, and Charlie's is sent first:

  submitting Charlie's tx FIRST; it declares Bob's tx (nonce 0) as parent
  2 blocks later the child is still not in any block: it waits for its parent
  now submitting Bob's parent tx
  parent: block #6 index 1 | child: block #6 index 2
  ok: the child executed strictly after its parent

How it is built on the Polkadot SDK

The pool is already a DAG

The Polkadot SDK transaction pool does not use a simple queue. Each transaction declares tags it provides and tags it requires, and it becomes ready only when everything it requires is provided. Normally the tags are (account, nonce): your transaction with nonce 5 provides (you, 5) and requires (you, 4). So every chain built with the Polkadot SDK already has a dependency graph. It just only links an account to itself.

One extension adds cross-account edges

CheckDagParents is a transaction extension. A transaction lists parents as (account, nonce) pairs. The extension does two things:

  1. In the pool: for each parent that has not executed yet, add a requires tag. The tag has exactly the encoding that the standard CheckNonce extension uses for provides. So the pool, unchanged, waits for the parent.
  2. When the block executes: check again that every parent has executed (its account's nonce has moved past the parent's nonce). If not, the transaction is invalid. A block producer that puts a child before its parent produces an invalid block, which every honest validator rejects.

The check runs before CheckNonce. That way a rejected transaction changes nothing, not even the sender's nonce. (An early version had them the other way round; a test caught it.)

No tips, no priority auction

In a standard Polkadot SDK chain, a higher tip gives a transaction a higher priority. That makes tips an open auction for position, which is exactly what front-runners pay for.

ChargeTransactionPaymentNoTip is the standard fee extension with one change: any tip is refused. It keeps the same name and encoding, so wallets keep working as long as they send a tip of zero.

  rejected by the pool as expected: Invalid Transaction: "Custom error: 0"

Limits

  • It only enforces declared dependencies. A transaction that names no parent can still be front-run by any transaction that does not depend on it. The whitepaper claimed that a DAG makes front-running "computationally infeasible"; that is not true (see What the original design got wrong). The fix for undeclared front-running is sealed ordering.
  • Eight parents at most, to keep the check cheap.

Sealed ordering against front-running

Code: pallets/sealed-ordering/

In plain words

To front-run you, someone must (1) see your transaction before it runs and (2) get their own transaction in ahead of it. Sealed ordering removes the second part:

  1. Commit: you (or a relayer for you) publish only a 32-byte fingerprint of your transaction, plus a deposit. Nobody can tell what it does. If a relayer submits it, nobody can tell who it is from either.
  2. Reveal: in the next two blocks, you publish the transaction itself.
  3. Execute: at the start of a later block, all revealed transactions from the same commit block run in an order that nobody chose and that nobody could predict when committing.

Someone who sees your reveal and wants to get ahead of you can only commit in a later block, and later blocks always execute after yours.

$ canggu sealed
  relayer committed 4 opaque 32-byte hashes in block(s) {3}: nobody can tell who pays whom
  Dave revealed in block #4 (index 1)
  Charlie revealed in block #4 (index 2)
  Bob revealed in block #4 (index 3)
  block #6: position 0: Bob (ok)
  block #6: position 1: Dave (ok)
  block #6: position 2: Charlie (ok)
  block #6: Eve never revealed, deposit burned
  ok: execution order = blake2(commitment ‖ commit-block hash), not reveal order

Where the idea comes from

This is adapted from the Rand Protocol whitepaper by Dendi Suhubdy (one of Canggu's original authors) and Anish Mohammed. Its Proposition 14.2 shows that hiding transaction contents is not enough, because the block producer can still order by metadata. Its Theorem 15.4 shows that front-running is removed only if three conditions hold:

  1. the order is fixed while the contents are still hidden;
  2. there is exactly one valid order, and it binds the block producer;
  3. what is visible before ordering does not tell transactions apart.

Rand meets condition 1 with threshold encryption (validators jointly decrypt after ordering). Practical threshold encryption today uses elliptic-curve pairings, which are not quantum-safe, and Rand's live chain does not implement it. Canggu uses hash commitments instead, which only need a hash function.

How it is built on the Polkadot SDK

The whole feature is one ordinary FRAME pallet with two calls and one hook.

StepPallet itemWhat happens
Commit (block N)commit(commitment)Stores BLAKE2b("canggu/sealed/v1", sender, call, salt) and holds a deposit (1 CGU).
Reveal (blocks N+1 to N+2)reveal(N, call, salt)Must come from the sender named in the commitment. Stores the call.
Execute (start of block N+3)on_initialize hookSorts revealed calls of block N by BLAKE2b(commitment ‖ hash of block N) and dispatches them. Returns deposits of revealed commitments; burns the others.

The hook runs at the start of every block, before normal transactions, so the block producer cannot place anything in between. The sort key uses the hash of block N, which nobody knows when they commit in block N.

Limits that keep the hook safe: at most 64 commitments per block, each sealed call at most 1/400 of a slot's time, and only calls of the Balances and Payroll pallets can be sealed.

What it does not do

CAUTION: Commit-reveal is weaker than threshold encryption in four ways.

  • A sender can decline to reveal (a "free option"). The deposit of whoever submitted the commitment is burned. If a relayer submitted it, the relayer pays, not the sender: a relayer must charge senders for that risk.
  • A block producer can refuse to include reveals (censorship).
  • The producer of block N can try to influence the hash of block N. That only reshuffles commitments whose contents nobody can see.
  • Back-running (acting right after a revealed transaction) is not prevented.

A further idea, not built: commitments could carry a ring proof from the verifiable library, proving "this came from some registered account" without a relayer. See Lessons from Rand Protocol.

Zero-knowledge proofs: Groth16 and SP1

In plain words

An employer wants to prove to the chain: "the salaries I am about to pay add up to this total, and they match the salary table I committed to earlier", without showing any salary. That is a zero-knowledge proof. The proof is made off-chain. The chain only checks it.

Canggu checks two kinds of proof:

How it is built on the Polkadot SDK

pallet-zk-verifier does not know any particular circuit. It accepts:

  • register_verifying_key and submit_proof for Groth16 proofs on BLS12-381;
  • submit_sp1_proof(program, public_values, proof) for SP1 proofs, where program is the SP1 program's 32-byte verification-key hash.

A proof that checks out is recorded as a statement (which program, which public values), so other pallets or apps can rely on it. A failed proof still pays its full fee.

Both checks are host functions, like signature verification:

#![allow(unused)]
fn main() {
fn groth16_bls12_381_verify(vk: &[u8], inputs: &[u8], proof: &[u8]) -> bool;
fn sp1_v6_verify_compressed(proof: &[u8], public_values: &[u8], vkey_hash: &[u8]) -> bool;
}

For SP1 this is not only about speed: SP1's verifier does not compile for wasm32v1-none, the target Polkadot SDK runtimes use. A host function is the only way to use it.

The payroll statement

Private inputs: a salt and N salaries. Public outputs: the total and a commitment to the salt and salaries. The two versions differ in detail:

  • Groth16 version (zk/): the salt is one field element, N is fixed when the keys are made, and the public inputs are [total, commitment]. The circuit has a MiMC hash commitment and a 64-bit range check per salary: 396 × N + 333 constraints (1,917 for 4 salaries). Proving 1,024 salaries takes 2.0 s on 12 cores.
  • SP1 version (sp1/programs/payroll): the salt is 32 bytes and the public output is N ‖ total ‖ commitment (52 bytes). The program is about 25 lines of Rust that sum the salaries with overflow checks and commit with Keccak. It needs no circuit design at all. Proving takes about 50 seconds for 16 salaries and 452 seconds for 262,144 salaries.
$ canggu zk-sp1 --from //Alice --salt "october payroll" --amounts 3000,4500,1250,8000,2200
payroll proved: 6137 cycles, 1272546 byte proof, 59.2 s
  submitting a 1.28 MB post-quantum proof
  ok: the chain verified that 5 private salaries sum to 18950
node: 🔐 SP1 compressed proof (1272546 bytes): valid in 41.95ms

A finding: one proof, many encodings

SP1's standard verifier accepts several different byte strings for the same valid proof. It ignores extra bytes at the end, and it silently reduces numbers that are too large for the field. That is harmless for "is this proof valid?", but a chain that stores, hashes or deduplicates proofs could be confused. Canggu's wrapper (canggu-sp1-verify) accepts only the exact canonical bytes. A test shows both the problem and the fix.

Limits

  • The Groth16 path is not quantum-safe and uses a single-party trusted setup. It is kept for comparison.
  • SP1 proofs are 1.27 MB: only a few fit in a block.
  • Weights are estimates, not benchmarks.

Signature compression with a zkVM

Code: pallets/pq-intents/, sp1/programs/mldsa-batch

In plain words

Post-quantum signatures are big: 5.3 kB of key and signature per transfer. That size, not CPU time, limits the chain to about 370 transfers per second.

Signature compression replaces many signatures with one proof that says "I checked all of these signatures, and they are all valid". The chain checks the proof instead of the signatures.

It works. It is also the clearest example in this project of an idea that only pays off at scale.

Step 1: intent batches

pallet-pq-intents lets users sign intents off-chain ("pay 1 CGU to Bob, this is my intent number 3"). A relayer collects up to 640 of them and submits them in one transaction. The runtime checks all signatures with one host call:

#![allow(unused)]
fn main() {
fn ml_dsa_65_batch_verify(items: Vec<(public_key, message, signature)>) -> Vec<bool>;
}

Each intent then succeeds or fails on its own (bad signature, wrong nonce, not enough balance). This one call is also where a GPU can help: see GPU verification.

Step 2: replace the signatures with one SP1 proof

sp1/programs/mldsa-batch is a Rust program that verifies ML-DSA-65 signatures. It runs inside the SP1 zkVM, which produces a proof that the program ran correctly. The program:

  1. verifies every signature in the batch (if one is invalid, no proof can be made);
  2. outputs a digest: n ‖ Keccak(context) ‖ Keccak(for each: account ‖ Keccak(message)), where account = BLAKE2b(public key).

submit_compressed then takes only (sender, intent) pairs and the proof: no keys and no signatures. The runtime rebuilds the digest from the intents and the chain's genesis hash, and asks the sp1_v6_verify_compressed host function whether the proof matches. Because the runtime computes the digest itself, the proof cannot be reused for other intents or on another chain.

$ canggu intents --count 8 --senders 4 --compressed
mldsa-batch proved: 5611080 cycles, 1272546 byte proof, 112.7 s
  relayer submits 1.28 MB (one SP1 proof, no keys or signatures) instead of 0.04 MB
  block #91: 8 intents executed, 0 rejected {}

The ML-DSA code inside SP1 gives the same answer as the ml-dsa crate on every test case (4,280 native cases and 460 runs inside the zkVM). SP1's Keccak precompile (a built-in accelerator for the hash function that ML-DSA uses heavily) cuts the cost from 1.83 million to 0.70 million cycles per signature.

The bigger design this points to

Rand Protocol (a chain by Dendi Suhubdy) solves the same problem for its own, much larger proofs: GPU "aggregators" prove one proof over a window of already-finalised blocks, off the critical path, and are paid for it. That pipeline is what would make compression pay off here too. It is not built. See Lessons from Rand Protocol.

Parallel payroll

Code: pallets/parallel-payroll/

In plain words

The Canggu whitepaper's main example is a payroll: an employer pays many employees at once. The whitepaper splits it into a CPU part (check the employer's balance and take the total once) and a GPU part (credit all employees in parallel).

pallet-parallel-payroll has one call, batch_pay, that does exactly that split:

  1. Sequential part: add up the payments (with overflow checks), check the employer can pay, and take the total from the employer once.
  2. Parallel part: credit each recipient.
=== 4. Payroll: one debit, conflict-free parallel credits ===
  5F3ohmaD…: +1000.0000 CGU
  5EKGfkiy…: +2000.0000 CGU
  5F3bxbZ4…: +1500.0000 CGU
  5FqiwtSw…: +2500.0000 CGU
  batch paying Bob twice: rejected with Payroll::DuplicateRecipient

What makes the credits "parallel"

The pallet refuses a batch in which a recipient appears twice, or in which the employer is also a recipient. Then every credit writes to a different account, so the credits can run in any order, or at the same time, and the result is the same. That property (disjoint writes) is what a parallel executor needs.

Why the credits still run one after another today

A Polkadot SDK runtime is single-threaded WebAssembly, and each credit is mostly a read and a write of the state database. A GPU cannot speed that up. The whitepaper's claim that 10,000 transfers take "under 1 ms" on a GPU confuses adding numbers with updating 10,000 database entries.

So the pallet guarantees the contract (no conflicts), not the speed-up. The speed-up would come from executing conflict-free work on several CPU cores, which is where Polkadot's newer designs (such as JAM) are going.

Limits

  • Weights are linear estimates, not benchmarks.
  • "Parallel gas" pricing (from the whitepaper) only makes sense once execution is really parallel. Until then, the chain charges single-core cost.

GPU verification with Apple Metal

Code: gpu/, node/src/accel.rs, primitives/src/accel.rs

In plain words

The Canggu whitepaper wants smart contracts that run on GPUs. That does not work on a chain whose execution must be deterministic and metered, for the reasons below. What does work is this: when a block contains hundreds of post-quantum signatures, a validator can check them all on its GPU, while another validator checks the same signatures on its CPU, and both always agree.

That is what this project does, on the GPU of an Apple M4 Pro laptop through Apple's Metal API.

Why the runtime itself cannot run on a GPU

  • Every validator must get identical results, bit for bit. GPU floating-point maths and the order of parallel sums vary between GPU models and drivers.
  • Execution must be measured and limited (weights). A GPU kernel cannot be stopped halfway or measured per instruction.
  • The chain's state lives in a database tree that GPU code cannot reach.
  • Requiring one vendor's GPU would shut out every validator without one.

The way that works: a GPU behind a host function

The runtime asks one question per batch: "which of these signatures are valid?" (the ml_dsa_65_batch_verify host function). The answer is a list of yes/no values, and it must be exactly the same however it is computed. The node chooses how to compute it when it starts:

canggu-node --crypto-backend <cpu | cpu-parallel | metal>

  cpu            reference implementation, 1 core        ← defines the correct answer
  cpu-parallel   reference implementation, all cores     (default)
  metal          ML-DSA-65 verification as Metal compute kernels
                   CPU: decode, checks, hash the key and message, build the challenge
                   GPU: NTTs → expand matrix A and multiply → UseHint → final SHAKE256 compare

Batches below 64 signatures go to the CPU, because sending work to the GPU has a fixed cost of about 0.2 ms.

How we know it is correct

Correctness matters more than speed here: a GPU that disagreed with the CPU on one signature would make its validator reject valid blocks.

  1. Three implementations agree. The Metal kernels, a pure-Rust copy of each kernel, and the RustCrypto ml-dsa crate were compared on 5,454 cases: 2,504 valid signatures and 2,950 damaged ones (flipped bits in every field, bad hints, edge values, wrong lengths and contexts). All three gave the same answer every time.
  2. A self-test at start-up. The node checks the GPU's arithmetic against the CPU (including one step for every possible input) before it accepts the GPU. During development this test caught a deliberately planted bug that real signatures never trigger.
  3. Two validators, two kinds of hardware. scripts/mixed-backends.sh runs Alice on the GPU and Bob on one CPU core. They take turns making blocks, so every batch is checked by the GPU on one validator and by the CPU on the other:
#6:  authored by Alice (metal), imported by Bob (cpu)
#7:  authored by Bob (cpu), imported by Alice (metal)
#8:  authored by Alice (metal), imported by Bob (cpu)
#9:  authored by Bob (cpu), imported by Alice (metal)
#10: authored by Alice (metal), imported by Bob (cpu)
#11: authored by Bob (cpu), imported by Alice (metal)
blocks 1..11: identical
finalized: alice #11, bob #11

Sub-second finality

Code: node/src/service.rs, scripts/finality.sh

In plain words

A block is final when it can never be undone. The Canggu whitepaper asks for finality in under a second. With the Polkadot SDK's default settings, a block becomes final about 5 seconds after it appears, which makes it look impossible.

It is not impossible. Two cautious default settings cause almost all of the delay. With both changed, two validators on one computer finalised blocks in a median of 242 ms with the normal 2-second blocks, and 121 ms when the block time was also shortened to 500 ms.

Where the 5 seconds come from

GRANDPA, the finality protocol, works in voting rounds. Two settings slow it down:

  1. Vote lag. By default validators vote for the block two behind the newest one, in case the newest one is about to be replaced by a competing block. With 2-second blocks, that alone adds 4 seconds. Lowering it does not make finality unsafe: a block is final only when more than two-thirds of validators agree, and votes for a block that loses simply finalise the last block both sides share.
  2. Gossip duration (default 333 ms). A validator waits up to 2× this before its first vote and 4× before its second.

Both are now node options: --grandpa-vote-lag and --grandpa-gossip-ms. The block time is a build option: CANGGU_SLOT_MS.

  • The gossip duration must be longer than the message delay between validators.
  • Each round needs about two message delays.
  • A validator set with 50–100 ms between members should still finalise in well under a second. A set spread around the world, with 200 ms or more between members, probably will not.

Nothing here was tested over a real network. The node's defaults stay at the Polkadot SDK's cautious values.

Why not use Polkadot's relay chain?

Running Canggu as a Polkadot parachain would give it shared security, but finality would come from the relay chain and be slower. It would also remove Canggu's custom host functions (relay validators only have the standard ones), so post-quantum signature checks, proof checks and the GPU backend would not work as built here.

What the original design got wrong

Building a design is the fastest way to test it. These are the claims from the Canggu v1.3 whitepaper that did not hold up. They are listed so that readers do not repeat them, not to take anything away from the authors' ambition.

Lessons from Rand Protocol

Rand Protocol is a later blockchain by Dendi Suhubdy, one of Canggu's original authors. Its whitepaper, Randprotocol: Confidential Arbitrary Computations, is by Dendi Suhubdy and Anish Mohammed. It makes many of the same choices (Dilithium, STARK proofs, GPU provers) on a different foundation. Comparing the two explains a lot about both.

One decision explains most differences

Rand is a fully shielded chain: no accounts, no balances, no visible senders. Canggu, like every Polkadot SDK chain, is an account chain.

What we took

  1. The corrected front-running theorem (Proposition 14.2 and Theorem 15.4), adapted with hash commitments instead of threshold encryption. See Sealed ordering.
  2. The signature-compression analysis. Rand's documents give the architecture (pipelined aggregation over finalised blocks, a GPU prover market, "the proof that covers the most wins", proofs bound to their maker) and its price: 26 minutes to prove an aggregate of one transfer in a test setup, and at least 512 GB of memory for a production proof. Canggu built the core (one SP1 proof per batch) and measured the same lesson. See Signature compression.

Is verifiable useful here?

verifiable proves "I am one of these registered members" without saying which one. It uses ring VRFs on the Bandersnatch curve, with 752-byte proofs and one unlinkable 32-byte alias per member per context.

  • Useful for front-running metadata. A sealed commitment could carry a ring proof that it came from some registered account, with one alias per epoch as a rate limit, instead of going through a relayer.
  • Not useful for signature compression. It provides anonymity, not aggregation; its proofs are larger than a plain signature and do not combine.
  • Not post-quantum. Its security rests on elliptic curves. Its interface, though, could front a post-quantum implementation (for example a STARK over a Merkle tree with nullifiers, which is how Rand's shielded pool works).

It was evaluated but not used in the code.

Why the Polkadot SDK made this possible

Canggu's whitepaper reads like a chain built from scratch: its own consensus, its own mempool, its own signature scheme, its own execution model. That is normally years of work. On the Polkadot SDK, almost every one of those turned out to be a hook the framework already had. This is the main lesson of the project.

The pattern to copy

If you want to build something "very complicated" on the Polkadot SDK, the pattern from this project is:

  1. Keep the rules in the runtime. Pallets and transaction extensions decide what must be true.
  2. Put heavy mathematics in host functions. The node decides how to compute it: native code, all cores, or a GPU, as long as the answer is always identical.
  3. Use the existing machinery before inventing new machinery. The transaction pool's tags, the fee extension and the block-initialisation hook replaced what looked like three new subsystems.
  4. Measure everything. Several of the most important results here are negative (signature compression does not pay off on a laptop; 50,000 TPS does not fit), and they came from measuring, not from reasoning.

Where the framework pushed back

The Polkadot SDK is not magic, and the places where it resisted are instructive:

  • Consensus keys. Making block production and finality post-quantum means changing the node's keystore and GRANDPA's vote format. That is deep node work, not a pallet.
  • Custom host functions tie you to a standalone chain. A Polkadot parachain is re-executed by relay-chain validators that only have the standard host functions.
  • Large proofs. Blocks have a size limit, and 1.27 MB SP1 proofs use a lot of it.
  • Dependencies move fast. Tooling around exact dependency versions took real effort.

Limitations and open problems

WARNING: This is a research prototype. It is not audited. Do not use it to hold or move real value.

Security

  • Only accounts are post-quantum. Block production (Aura, Sr25519), finality votes (GRANDPA, Ed25519) and the peer-to-peer handshake still use classic cryptography. A quantum attacker could forge blocks or votes.
  • The Groth16 path is not post-quantum and uses a single-party trusted setup (demonstration only). The SP1 path is the quantum-safe one.
  • Weights are estimates. No pallet has benchmarked weights, so fees and block limits are approximate.
  • Nothing is audited: not the pallets, not the GPU kernels, not the SP1 programs, not the MiMC circuit.

Front-running

  • Sealed ordering uses commit-reveal, not threshold encryption. Senders can refuse to reveal (the committer's deposit is burned; with a relayer, the relayer loses it), block producers can censor reveals, and back-running is not prevented.
  • Dependency ordering only protects transactions that declare their parents.

Performance and scale

  • About 370 transfers per second, limited by the size of post-quantum signatures.
  • Signature compression is a net loss below about 242 signatures per proof, and proving that many takes about 37 minutes on a laptop CPU. A GPU prover market is not built.
  • The GPU backend is Apple Metal only. There is no NVIDIA backend.
  • Finality was measured on one computer only. Real network delay was not tested.

Testing

  • Everything was built and measured on one Apple M4 Pro laptop. Linux builds and the Dockerfile are not tested.
  • The CI workflow in the repository is from the original project. It runs only on pull requests and does not match the current code.

Open problems worth working on

  1. Post-quantum session keys for Aura and GRANDPA.
  2. Threshold-encrypted mempool (needs post-quantum threshold decryption, an open research topic).
  3. Anonymous sealed commitments with ring proofs.
  4. GPU provers and windowed proof aggregation, following Rand Protocol's design.
  5. Benchmarked weights, and finality measured over a real network.

Glossary

Aura: The Polkadot SDK's block-production method. Validators take turns, one per time slot.

BLAKE2b: The hash function Polkadot SDK chains use. Canggu derives account addresses from ML-DSA public keys with it.

BLS12-381: An elliptic curve used by Groth16 proofs. It is not safe against quantum computers.

Commitment: A hash that fixes a value without showing it. Sealed ordering uses commitments to fix the order before contents are known.

CUDA: NVIDIA's GPU programming system. Not used here; the Metal backend is Apple's equivalent.

DAG (directed acyclic graph): A set of items with "comes after" arrows and no loops. Transactions with dependencies form one.

Deterministic: Always giving the same output for the same input. Runtimes must be deterministic so every validator agrees.

Extrinsic: The Polkadot SDK's word for a transaction (or other data put into a block from outside).

Finality: The point after which a block can never be undone.

FRAME: The Polkadot SDK's framework for building runtimes out of pallets.

GRANDPA: The Polkadot SDK's finality protocol. Validators vote; a block with votes from more than two-thirds of them is final.

Groth16: A zero-knowledge proof system with very small proofs (192 bytes) and a trusted setup. Not quantum-safe.

Host function: A function the node provides to the runtime. The runtime calls it; the node runs it as native code.

Intent: In Canggu, a transfer signed off-chain and submitted in a batch by a relayer.

Keccak / SHAKE: A family of hash functions. ML-DSA uses SHAKE heavily; SP1 has a fast built-in (precompile) for it.

MEV (maximal extractable value): Profit a block producer can make by choosing, adding or reordering transactions, for example front-running.

Metal: Apple's GPU programming interface.

ML-DSA (FIPS 204): The NIST post-quantum signature standard, formerly CRYSTALS-Dilithium. Canggu uses the ML-DSA-65 parameter set.

ML-KEM (FIPS 203): The NIST post-quantum key-exchange standard, formerly CRYSTALS-Kyber. It cannot sign.

Nonce: A counter per account. Each transaction uses the next number, so it cannot be replayed.

Pallet: A module of a FRAME runtime, with its own storage, calls and events.

Parachain: A chain that gets its security from Polkadot's relay chain. Canggu is not one; it is a standalone chain.

Post-quantum: Believed to stay secure against large quantum computers.

Precompile: A built-in, accelerated operation in a virtual machine (here, Keccak in SP1).

Relayer: Someone who submits other people's signed data (intents, commitments) and pays the fee.

Runtime: The chain's rules, compiled to WebAssembly and stored on-chain.

Shor's algorithm: A quantum algorithm that breaks the elliptic-curve and factoring problems behind today's signatures.

SP1: A zkVM by Succinct Labs that proves Rust programs compiled to RISC-V.

STARK: A family of proof systems that use only hash functions. No trusted setup; plausibly post-quantum; large proofs.

Transaction extension: A check that runs before and after every transaction (nonce, fee, mortality (era), and Canggu's dependency check).

Weight: The Polkadot SDK's measure of execution time. Blocks have a weight limit; fees follow weight.

zkVM: A zero-knowledge virtual machine: it proves that a normal program ran correctly.
