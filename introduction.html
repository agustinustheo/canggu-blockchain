Canggu on the Polkadot SDK

Canggu on the Polkadot SDK

⚠️ 🚧 For learning only. Use at your own peril. 🚧 ⚠️

This is a research prototype that explores how far the Polkadot SDK can go. It is not audited and it is not production software. Do not use it, or its development keys, to hold or move real value.

How far can the Polkadot SDK go?

This book documents an experiment. We took Canggu, an ambitious blockchain design, and tried to build it on the Polkadot SDK, the Rust framework that includes Substrate and FRAME. Canggu asks for things that sound like years of work:

  • accounts that stay safe when large quantum computers arrive;
  • zero-knowledge proofs, including proofs from a zkVM (a virtual machine that proves it ran a program correctly);
  • protection against front-running (MEV);
  • smart-contract-style work on GPUs;
  • finality in under a second.

The result is a working chain. It produces blocks, verifies post-quantum signatures, checks zkVM proofs on-chain, verifies batches of signatures on an Apple GPU, and keeps two validators in consensus while one uses a GPU and the other a CPU. Every performance number of this project in this book was measured on a real machine (an Apple M4 Pro laptop); numbers quoted from other projects are marked as such. Every limitation we found is written down.

This is not our idea. Canggu was designed by Dendi Suhubdy, Tejveer Singh, Mitul Dhawan and Maldini Sonkeng (Bitwyre), who wrote the original whitepaper and open-sourced it. This rebuild was written by Claude, an AI model made by Anthropic, in a conversation directed by agustinustheo, who published it. What is in the box

Canggu ideaHow it was built hereStatus
Quantum-safe accounts (Dilithium)A new account signature type (ML-DSA-65) checked by native node codeWorks
Transactions that cannot be reordered past their dependenciesThe transaction pool's existing dependency graph, plus one extensionWorks
Front-running protectionNo tips, and sealed ordering: commit now, reveal later, run in an order nobody choseWorks, with known trade-offs
Zero-knowledge proofsGroth16 (small, not quantum-safe) and SP1 zkVM proofs (large, quantum-safe)Works
Signature compressionOne SP1 proof replaces every signature in a batchWorks, but only pays off with large batches and GPU provers
GPU accelerationBatch signature verification on Apple Metal, behind a node functionWorks
Fast leader-based consensusAura block production and GRANDPA finalityWorks
Sub-second finalityGRANDPA with two settings changed: 242 ms with 2 s blocks, 121 ms with 500 ms blocks, on one machineWorks on localhost; not tested over a real network
50,000+ transactions per secondNot reached: about 370 per second, limited by signature sizeNot possible as designed
